모바일본부 공용 크래시 분석 에이전트 플러그인

PERIOD
2026.09 — 현재

조회를 서브에이전트로 분리한 구조

DECISION
  • 메인 세션엔 직접 조회 없이 결론 · 파일 경로 주입(원본 응답은 서브에이전트 내부에서 처리)
  • 모듈끼리는 서로 모르게 분리, 연결 키(유저 · 시각 / 커밋 · 크래시 지점)는 오케스트레이터를 통해 전달
  • 도메인 지식은 스킬로 단일화 → 에이전트 정의엔 격리 이유 · 반환 계약 · 실패 규칙만
  • 모듈 간 파일 계약으로 키 이름 · 허용값까지 고정, 값도 요약 문장 대신 파일에서 참조
  • 묻기 · 클론 · 공용 노트 기록은 오케스트레이터 전용, 서브에이전트는 산출물 파일로 작성
WHY
  • Crashlytics 이벤트 응답이 비대해 메인 세션의 컨텍스트를 아끼기 위해
  • 같은 지식을 에이전트와 스킬에 중복 정의해 정반대로 갈린 사례 2건
  • 요약 문장으로 전달한 값이 잘려 리포트에 "근거 없음" 으로 누락된 사례

크래시 한 건 분석 흐름

DECISION
  • 조회 완료 후 행동 로그와 소스 대조를 병렬 실행(둘 다 조회가 추출한 연결 키에만 의존)
  • 크래시 당시 커밋으로 코드 고정(시점 추적), 없으면 기준 브랜치로 대체해 스택 프레임마다 대체 여부 표시
  • iOS 는 커밋 해시가 없어 버전 태그 · 릴리스 브랜치로, 공용 C/C++ 코어는 버전 → SDK 태그 → 서브모듈 핀 순으로 추적
  • cherry-pick 시 해시가 바뀌므로 릴리스 포함 여부는 patch-id 로 판별
  • 저장소가 없으면 묻기, 건너뛰면 대조 못 한 범위를 리포트에 표시
  • 확인(건수 · 분포 · 코드 · 행동 시각)과 가설(원인 · 재현 · 수정) 분리, 가설에는 근거와 반증 조건 명시
WHY
  • 스택이 가리키는 코드가 크래시 당시 코드가 아니면 분석 전체가 무의미(최신 코드로 대조하면 이미 바뀐 다음 버전 코드를 보게 됨)
  • HEAD 는 개발자의 피처 브랜치일 수 있음
  • 없는 소스를 추측으로 메우면 오류 없이 조용히 틀림
  • 서브에이전트는 사용자에게 질문 불가 → 오케스트레이터 담당
  • "확인 못 함" 을 "아님" 으로 합치면 확인한 적 없는 항목이 "없음" 으로 확정 보고
RESULT
  • 실제 크래시 5건 처음부터 끝까지 원인 확정(Android 앱 · iOS · Android 네이티브)
  • 1건은 수정이 릴리스 브랜치에만 반영되고 기본 브랜치엔 빠져 다음 작업에 결함이 남는 문제까지 추적

검증

  • 이미 고친 크래시를 다시 분석해 제안한 수정과 실제 수정 방향 대조
  • 실제 크래시 5건을 처음부터 끝까지 분석해 원인 확인
  • 같은 질문을 플러그인이 있을 때와 없을 때로 나눠 답변 비교
  • 리포트는 실데이터로 렌더링, 문서의 전제는 실제 API 호출로 확인

플랫폼별 분기

  • Android 네이티브(C/C++)는 Play Vitals 에서 조회
  • iOS 는 Crashlytics 에서 조회
  • 공용 C/C++ 코어 크래시는 두 콘솔에 절반씩 분산
  • Play Vitals 는 유저 식별자가 없어 행동 로그 단계 생략
  • ANR 은 소스 대조 대신 기기 · OS 쏠림부터 확인

설치 · 피드백

  • 설치 · 로그인 · 권한 상태 점검
  • 초기 설정 가이드
  • 테스터 결과 수집(유저 ID 제외)
  • 단계별 소요 시간 측정

분석 규칙

  • 조회 기간은 기본값 없이 링크 → 사용자 지정 → 묻기 순
  • 난독화 스택은 심볼로 파일을 찾고 라인 매핑
  • 특정 기기 · 버전에 몰렸는지는 평소 사용 비율과 비교해 판단
  • 저장소는 origin 주소로 판정
