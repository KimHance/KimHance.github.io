Mobile · Design system

–디자인 시스템

스펙 문서를 먼저 쓰고 지켜지지 않는 규칙은 코드로 옮긴 Compose 디자인 시스템

PERIOD
2024.12 — 2025.09

규칙을 코드로

PROBLEM
  • RN 앱을 네이티브로 다시 쓰며 UI 체계를 새로 세워야 하는 상황
  • Atomic Design 으로 나눴지만 컴포넌트가 늘수록 지켜지지 않는 분류 규칙
  • 수작업 카탈로그 목록이 실제 코드보다 늘 뒤처진 상태
DECISION
  • 스펙 문서 먼저 작성, 지켜지지 않는 규칙은 코드에 내장
  • 컴포넌트에 Annotation 을 추가하면 빌드 시 KSP 로 컴포넌트 목록 생성
  • Figma API 로 공통 아이콘 목록을 불러와 업데이트 대상 선택 → SVG 를 XML 로 변환 → MR 생성
WHY
  • 문서에만 적힌 규칙은 지키기 어려움
  • 카탈로그는 별도 앱이라 기획 · 디자인이 정책과 동작을 직접 확인
RESULT
  • 카탈로그 목록 · 아이콘 반영의 수작업을 Annotation 추가와 아이콘 선택으로 축소

Interaction

PROBLEM
  • 플랫폼 · 컴포넌트마다 흩어져 있던 Interaction 스펙
  • 컴포넌트마다 Indication 을 새로 만드는 구조
DECISION
  • Interaction 스펙을 먼저 작성한 뒤 iOS · 디자인과 함께 정리
  • Indication 팩토리로 분리(layer · scale · scale + layer)
WHY
  • Modifier 팩토리는 clickable · toggleable 등 상호작용 종류마다 따로 만들어야 하지만 Indication 팩토리는 Indication 파라미터가 있는 모든 곳에서 재사용
RESULT
  • 공통 컴포넌트 Indication 을 Figma Interaction 기준으로 다시 적용
