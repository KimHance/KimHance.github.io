–앱 품질 정량화

최적화할 곳을 측정으로 찾고 개선 여부까지 확인하는 앱 성능 정량화 체계

PERIOD
2026.06 — 현재

측정 기준 설계

PROBLEM
  • 어디가 얼마나 느린지, 최적화 후 개선됐는지 같은 기준으로 확인할 방법 부재
  • 리팩토링 전후 스크롤 버벅임을 비교할 공통 지표 부재
DECISION
  • 측정 → 최적화 범위 특정 → 최적화 → 재측정(개선 확인) 순환 설계
  • 구글 표준(Vitals · App Performance Score) 차용, 종합 점수 대신 영역별 지표로 분리
  • 지표 정의 · 측정법 · 프로파일 원리까지 문서로 정리
WHY
  • 기준선 없이는 개선 여부 판단 불가 → 첫 측정값을 기준선으로
  • 측정자가 바뀌어도 같은 수치가 나오는 재현성 필요

벤치마크 하네스

DECISION
  • 자연어 요청을 작성 스킬이 측정 유형 질문 → 기획서 → 플랜으로 구체화, 검증 에이전트 검토 뒤 시나리오 코드 생성
  • 측정 유형(절대 성능 · 변경 효과 · 프로파일 효과 · 프로파일 생성 · 기능 검증)에 따라 지표 · 컴파일 모드 · 실행 방식 결정
  • 공통 액션을 먼저 재사용하고, 없는 동작만 화면 전용 액션으로 추가
  • 실행 스킬 · 로컬 대시보드에서 기기를 골라 실행, 분석 에이전트가 결과 리포트 작성
  • 벤치마크는 실행마다 별도 Gradle 프로세스 · 실행 큐로 순차 실행, 종료 시 빌드 설정 자동 원복
WHY
  • 측정 유형마다 맞는 지표 · 컴파일 모드가 다름 — 두 조건을 한 번에 바꾸면 결과 해석 불가
  • 한 번 잰 수치는 기기 상태 · GC · 스케줄링에 따라 변동 → 반복 측정하고 분산으로 안정성 판단
  • 측정에 익숙하지 않은 팀원도 같은 수치를 낼 수 있어야 팀 단위 도입 가능
  • 여러 실행이 같은 빌드 출력을 공유하면 충돌 → 한 번에 하나씩 실행
RESULT
  • 벤치마크 코드를 직접 작성하는 대신 자연어 요청으로 측정 — 측정 비용 축소
  • 늦게 뜨는 팝업 반복 닫기 · 중첩 클릭 회피 · 화면 표시 후 진입 판정 — 시나리오가 실패해도 통과로 기록되던 문제 차단

ColdStart 최적화(적용 사례)

PROBLEM
  • Play 콘솔의 느린 콜드 스타트 비율이 동종 앱 중앙값보다 높음
  • 사내 구동 지표는 스플래시부터 측정 → 프로세스 시작 ~ 첫 프레임 구간 누락
DECISION
  • 측정 범위를 프로세스 시작 ~ 첫 콘텐츠 표시로 재정의 후 Startup · Baseline Profile 적용
  • 프로파일 생성과 시작 벤치마크에 같은 홈 진입 시나리오 사용
  • Startup Profile 은 실제 서버 응답으로 리스트 로드까지 진행해 생성, 스크롤 벤치마크는 목 데이터로 측정
  • Baseline Profile · Startup Profile 함께 적용, Macrobenchmark 로 적용 전후 비교
WHY
  • Baseline Profile — 포함된 코드 경로를 설치 시 ART 가 AOT 컴파일해, 첫 실행부터 인터프리터 · JIT 단계를 건너뜀
  • Startup Profile — 빌드 시 R8 이 시작 코드를 첫 DEX 파일(classes.dex)에 모아 배치(DEX 레이아웃 최적화)
  • 프로파일을 만들 때 거치지 않은 화면의 코드는 프로파일에 들어가지 않음 → 측정하는 화면과 다르면 효과가 측정되지 않음
  • 시작 구간 — 리스트 로드까지 진행해야 네트워크 · 직렬화 · 디코딩 코드가 프로파일에 포함
  • 스크롤 측정 — 목 데이터로 네트워크 응답 시간에 따른 노이즈 제거
RESULT
  • TTID 중앙값 646 → 549ms(−15%) · 콜드 스타트 → 첫 썸네일 중앙값 3,117 → 2,509ms(−19.5%)
  • 배포 후 Play 콘솔 콜드 스타트 p90 · 느린 콜드 스타트 비율 · 사내 첫 썸네일 분포 모두 개선

실사용 모니터링(진행 중)

DECISION
  • 개발 모드 전용이던 프레임 수집기를 분리해 인앱 인스펙터 · GA4 가 같은 집계를 사용
  • 프레임 분포를 70구간 히스토그램으로 압축, 백그라운드 전환 시 화면별 1건 전송
  • 분위수 × 프레임 수로 전송 → 서버에서 합한 뒤 전체 프레임 수로 나눠 가중 평균
  • Vitals 기준(16ms · 50%) 고정, 디버그 빌드 제외, 프레임 처리 중 할당 없음
WHY
  • 모든 프레임을 보낼 수는 없고, 세션마다 프레임 수가 달라 분위수를 그대로 평균 내면 오차 발생
  • 버벅임 총 시간은 스크롤 양에 비례해 증가 → 빈도 · 심각도로 분리
  • 기기별로 다른 버벅임 판정 기준 적용 시 집계 왜곡
RESULT
  • 활성화 전 수집 On/Off 부하 비교에서 13개 지표 중 12개 차이 없음, 앱 CPU 차이 1.4%p 도 측정 편차 이내
  • 레거시 홈의 버벅임이 다른 화면보다 많이 감지 → 멈춰 있던 홈 리팩토링 재개 · 가속의 근거로 사용
  • 화면당 한 줄로 적용 → 다른 파트 화면으로 확산 중
  • 현재 수집 대상은 Jank, 크래시(mobile-debuggy 연계 예정) · 리소스 모니터링은 계획 단계
홈 리팩토링 →

PerfTracker페이지 →

  • adb 연결로 릴리즈 빌드 앱 덤프 추출, 지표 8개를 결과 파일 하나로 작성
  • 소스가 없는 앱도 같은 기준으로 측정

mobile-debuggy페이지 →

  • 모바일본부 공용 크래시 분석 에이전트 플러그인
  • 크래시 모니터링과 연계 예정

팀 도입

  • 안정성 대응 문서의 내부 측정 방법 5개 중 3개로 지정(벤치마크 모듈 · PerfTracker · 인앱 인스펙터)
  • 화면별 버벅임 지표의 다른 파트 화면 확대 지시
  • VOD 리팩토링 성능 테스트에 벤치마크 스킬 사용 협의
  • 플레이어 통계 화면에 인스펙터 화이트리스트 정책 적용 검토

문서
