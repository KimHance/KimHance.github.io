오래된 홈을 한 번에 바꾸지 않고 라이브 탭부터 전환 · 출시해 결과를 확인한 뒤 전 영역으로 넓히고 있습니다.

PERIOD
2025.09 — 현재

Summary

PROBLEM
  • 세 탭이 app 모듈의 거대한 화면 하나 · ViewModel 하나를 공유, 오래된 코드가 많아 수정 어려움
  • 수많은 RecyclerView 홀더 · 흩어진 상태 · app 모듈에 얽힌 의존성 · View 홀더 광고
DECISION
  • 한 번에 바꾸지 않고 단계별로, 라이브 탭을 먼저 전환 · 출시해 품질 · 안정성 확인 뒤 전 영역으로 확대
  • 1단계는 라이브 탭 화면을 Compose 그리드 하나로, 흩어진 상태를 MVI 하나로, 광고를 컴포저블로 바꿔 화면에 주입
  • 2단계는 세 탭 상태를 Circuit 으로, 도메인은 서버 그룹 구조를 평탄화 없이 그대로, 목록은 사내 공용 Paging 3 라이브러리로
WHY
  • 오래된 코드가 많아 한 번에 바꾸기 어려움 — 단계를 나눠 한 탭씩
  • 라이브 탭은 리스트 미리보기 플레이어가 없어 가장 먼저 옮기기 쉬운 탭
  • 화면별 Jank 모니터링에서 레거시 홈이 다른 화면보다 버벅임이 많이 감지 → 우선순위에 밀려 멈춰 있던 2단계를 재개하는 근거
  • Compose 에 어울리는 아키텍처로 MVI 선택
RESULT
  • app 모듈에 얽혀 있던 홈을 홈 모듈로 분리하고 MVI(Circuit) 적용
  • 비대한 ViewModel 의 상태를 Presenter 와 produce 패턴으로 분리 관리
  • 도메인 재설계로 서버의 그룹 구조를 그대로 사용해 평탄화 후 다시 그룹화하던 불필요한 작업 제거
  • 테스트하기 쉬운 도메인 구조로 홈 테스트 5 → 263건
  • 홈 스크롤 벤치마크에서 가장 느린 프레임 103.4 → 35.9ms(−65%), 프레임당 처리 시간 −21%
  • Paging 3 적용으로 라이브 탭 마지막 페이지까지 더 빠르고 부드러운 페이징

단계

◉ 펼치기 · 페이지 → 를 누르면 자세히 볼 수 있습니다

  1. 2025.09 – 12

    라이브 탭을 Compose · MVI 로 먼저 전환해 출시하고, 썸네일 캐시 방식을 바꿔 OOM 을 줄였습니다.

  2. 2025.12 –

    추천 · 이슈 탭까지 Circuit 으로 옮기고, 홈 도메인을 다시 설계했습니다.

  3. 2026.08

    Jank 모니터링으로 리팩토링 재개페이지 →

    화면별 Jank 모니터링에서 레거시 홈의 버벅임이 다른 화면보다 많이 감지되어, 멈춰 있던 2단계를 재개하고 일정을 앞당겼습니다.

  4. 2026.08 – 09

    Paging 3 를 화면마다 따로 구현하지 않도록 사내 공용 라이브러리로 만들고, 홈 라이브 탭에 처음 적용했습니다.

2025.09 – 12

1단계 — 라이브 탭 Compose 전환 · 출시

PROBLEM
  • 세 탭이 app 모듈의 거대한 화면 하나 · ViewModel 하나를 공유 · 의존성이 얽혀 한 번에 분리 어려움
  • 상태는 여러 Flow 로 흩어져 화면 곳곳에서 각자 구독
  • 광고는 거대한 View 홀더 · 영역을 하나씩 순차 호출
  • 라이브 썸네일은 최신 장면을 보여 주는 정책 때문에 예전부터 캐시가 꺼져 있었음 — 캐시 풀이 없어 썸네일을 많이 불러오면 OOM
DECISION
  • 라이브 탭만 분기 — 추천 · 이슈 탭은 기존 경로 그대로
  • RecyclerView → Compose 그리드 하나, 흩어진 상태는 MVI 하나로 · UI 는 feature 모듈로
  • 광고 View 홀더 → 컴포저블(SDK 광고는 AndroidView), 화면에는 slot 으로 주입
  • 광고 조회는 도메인 UseCase 로 옮겨 영역별 병렬
  • 원인 프로파일링 · 정책 합의 요청 → 10초 단위 시각을 키로 한 썸네일 메모리 캐시 적용(10초 안엔 재사용, 지나면 새로 로드 · 디스크 캐시 미사용)
WHY
  • 오래된 코드가 많아 한 번에 바꾸기 어려움 — 단계를 나눠 한 탭씩
  • 라이브 탭은 리스트 미리보기 플레이어가 없어 가장 먼저 옮기기 쉬운 탭
  • Compose 에 어울리는 아키텍처로 MVI 선택
  • 썸네일 주소가 늘 같아 주소만 키로 캐시하면 첫 이미지가 계속 노출 → 캐시를 꺼 둔 이유
  • 키에 10초 단위 시각을 더해 최신화 정책 유지, 메모리 상한은 캐시 풀(LRU)이 관리 · 10초마다 바뀌는 이미지라 디스크 캐시 불필요
RESULT
  • 도메인 구조 변경 · 광고 순차 → 병렬 조회로 목록 · 광고 조회 속도 개선
  • 광고 컴포저블화 — Compose 화면에서 광고를 바로 사용 가능
  • 썸네일 메모리 일정 수준 유지, 출시 전후 한 달 앱 OOM 상위 5개 감소

2025.12 –

2단계 · 홈 전체

PROBLEM
  • 1단계 방식의 한계 — 로직이 app 모듈에 남아 홈이 app 모듈의 ViewModel 을 직접 참조
  • 화면은 그리드, 데이터는 RecyclerView 시절 평탄화된 리스트라 여백 · 높이 · 광고 위치를 앞뒤 Item 에서 역산
  • 광고 인덱스가 프로세스 전역 변수라 병렬 조회 시 순번 뒤섞임
DECISION
  • 세 탭 Circuit 전환 — 상태는 feature 모듈이 소유(파트 개발자들과 협업)
  • 홈을 app 모듈 밖으로 옮기면 메인 화면 상태에 직접 닿을 수 없음 → 두 모듈 사이 통로(브릿지) 하나로 공유 상태만 전달
  • 도메인 1차(2026.05) 거대 매퍼 분리, 기존 매퍼와 출력이 같은지 테스트로 확인 후 삭제
  • 도메인 2차(2026.09) 서버 그룹 구조를 그대로 담는 모델, 기존 화면 옆에 새 화면을 두고 탭 진입만 교체
WHY
  • 그리드가 그룹별 렌더링을 지원해 평탄화 전제 불필요
  • 목록 밖 상태를 따로 두면 화면이 두 번 갱신되며 스크롤 위치가 밀림 → Item 전부를 스트림 하나에
  • 1단계 운영에서 겪은 광고 키 · 뷰 재사용 · 빈 목록 문제를 설계 규칙으로 고정
RESULT
  • 세 탭 모두 새 구조로 — 그 위에서 로그 · 플레이어 작업까지 팀 전체가 진행
  • 홈 테스트 5 → 263건
  • 광고 버그 3건 수정(첫 그룹 판정 · 순번 뒤섞임 · 채우지 못한 SDK 광고 잔류)
  • 세 탭 공통 컨테이너 · 상태 홀더 직접 구현
  • 그리드 키를 문자열로 고정, 릴리즈 난독화로 이름이 겹쳐 생긴 Item 재사용 오류 방지
  • 로드 실패 시 이전 데이터 폐기 정책 유지 · 벤치마크용 목 데이터는 릴리즈에서 차단
  • 썸네일 미리보기 재생 · 백그라운드 새로고침 구현

2026.08 – 09

Paging 3 사내 공용 라이브러리

PROBLEM
  • 홈 도메인이 페이지 누적 · 중복 제거를 직접 처리
  • 클라이언트 필터링으로 모자란 목록은 다음 페이지를 직접 호출해 보충
DECISION
  • androidx Paging 3 위에 사내 공용 라이브러리 모듈, 사용처는 이 모듈에만 의존
  • 페이지 조회 · 이어 붙이기는 라이브러리, 페이지 내용은 도메인이 담당
  • 공용 페이지 소스가 키 관리 · 누적 · 중복 제거 · 재시도 · 최소 개수 채우기를 모두 담당
  • 로딩 · 에러 · 빈 목록 · 콘텐츠 판정은 UI 프레임워크와 무관하게 제공 — RecyclerView 화면도 같은 판정 사용
WHY
  • Pager 는 래핑하지 않고 그대로 노출 — 래핑하면 append · refresh · retry 를 직접 호출할 수 없음
  • androidx Paging 버전은 라이브러리 모듈 한 곳에서 관리
  • 아이템 개수만으로 빈 목록을 판단하면 로딩 중에 빈 화면이 보임 — 로드 상태까지 함께 확인
RESULT
  • 팀 공용으로 먼저 배포, 샘플 앱 · 문서 6장 · 테스트 120건
  • 홈 라이브 탭에 첫 적용 — 클라이언트 필터링으로 모자란 목록을 다음 페이지를 직접 호출해 채우던 코드를 PageFillPolicy.untilAtLeast(minCount · maxSourcePages · countIf) 설정으로 대체
